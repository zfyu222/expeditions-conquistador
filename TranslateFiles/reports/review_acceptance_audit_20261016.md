# 独立审校复查通过率偏低：流程排查

日期：2026-10-16。范围：已归档的独立审校第1至第4轮、对应任务原始结果与实际交付的 handoff 输入包，以及共享流程源码。未运行翻译、重审、修复派发或修改工作流数据库。

## 结论

主要瓶颈是审校记录协议与提示词冲突，不能据此推断译文正确率偏低。不是笼统的“三项证据缺失”：第3轮此类失败的1,474条全部具备 logic 检查，但 status 使用了 not_applicable；其中1,473条为纯该错误，另1条同时报告术语回退。现有校验器要求非空原文的 accuracy、completeness、logic 均显式填写，状态只能为 pass/corrected，并附非空 evidence。

各分类互斥并合计为本轮失败数；术语回退另列为重叠标签，第1至4轮分别为59/4/3/3条。术语门槛失败可能需要语境例外，不能自动认定为误译。审校记录协议包括字段、状态、证据引用、修改记录和例外结构；证据内容本身仍需语义审查，不能全部视为可机械修复的格式错误。

重要限制：validate_body_row 遇到首个错误即抛出，review_scan 每条只保存一条主诊断。因此这些是“已观察到的首个失败门槛”，不是术语、结构或语义问题的完整发生率。格式失败项的后续检查可能未执行，0条 blocking 也不表示没有语义问题。不能用排除协议失败后的比例计算译文正确率。

## 根因与证据

### 1. not_applicable 的提示与校验规则直接冲突

`Tools/localization/translation_workflow.py:1184-1187` 给所有六维检查统一列出 pass/corrected/not_applicable，并要求“无相关内容时写 not_applicable 并解释”，没有写出三个必查维度的例外。`workflow_quality.py:35-37` 却禁止非空文本 accuracy/completeness/logic 使用 not_applicable。技能质量文档已说明限制，但实际单批输入包要求子代理只读本文件，所以不能依赖外部文档补足协议。

| 轮次 | 此类失败（含回退后缀） | logic 不适用 | accuracy 不适用（可重叠） | 其中译文未改 | 与上轮同类失败重复的ID |
|---|---:|---:|---:|---:|---:|
| 1 | 1,819 | 1,819 | 0 | 1,786 | — |
| 2 | 1,587 | 1,587 | 14 | 1,553 | 1,523 |
| 3 | 1,474 | 1,474 | 0 | 1,431 | 1,431 |
| 4 | 1,377 | 1,377 | 0 | 1,342 | 1,360 |

示例：Chieftain's House、Xalapa 等短标签的结果明确写了 accuracy/completeness 的 pass 及依据，logic 则说明“孤立标签，没有动作命题、否定、条件或数量关系”，并标记 not_applicable。这里实际有核对记录，失败原因是状态违反契约。依据是否充分仍需独立审查，不能直接批量将状态改成 pass。

核对各轮失败任务已提交输入包：236/75/47/39个任务的输入包全部仍包含这条歧义指令。这不是只存在于当前源码的推测，历史实际交付也有冲突。

### 2. 复查会交付旧证据和诊断，但没有给出可执行的字段修复要求

`workflow_review_rounds.py:174-191` 的修复任务确实包含 diagnostic、candidate、原文、正式译文及修复约束，并要求“只修复本批诊断及审校证据”。因此不能认定修复任务完全没有传审校证据。

缺口是诊断只说 Meaning/completeness/logic checks cannot be skipped，没有指出本条具体是 checks.logic.status，也没给出允许值和短标签处理方法；新一轮仍复用冲突提示词。候选保留了旧 not_applicable，修复者再次作出同样解释并原样保留状态，即可反复失败。第3轮的1,474条中有1,431条上轮已因同类问题失败，证实循环没有有效收敛。

后续轮次仅包含难以消除的失败项，分母持续缩小；协议错误越来越集中，导致轮通过率递减。不能解释为译文在每轮持续变差。

### 3. 修改证据摘录存在未明示的相等约束

`workflow_quality.py:49` 要求每条 changes[].source_excerpt 与该记录顶层 source_excerpt 完全相等；提示词只写两处都提供 source_excerpt，没有明确必须逐字相同。

第3轮59条 Invalid review change evidence 全部存在该不等问题，共61个 change 对象命中；第4轮52条也全部命中，共53个 change 对象。模型可能分别选取两个不同的有效原文摘录，但当前协议仍拒绝。它们属于修改证据契约失败，不能仅凭这一诊断认定修订译文错误。

### 4. 其他序列化问题及反馈时机

首轮另有 exceptions 类型错误356条、source/reason 缺失106条、顶层摘录不合规335条，以及整批40条级别的 checks/审校声明/issues/changes 格式问题。它们能被 JSON 解析并保存，问题主要发生在字段契约层，不能笼统称为 JSON 无法序列化。审校协议先给出精简 records 示例，再在后段补齐六维证据，增加遗漏风险。

batch-finish 延后所有证据校验，整轮结束才发现系统性格式错误；重复错误统一进入质量修复轮，亦计入同一修复预算。整轮统一语义验收本身符合现有规则，但缺少明确的协议反馈和格式诊断分类，使格式问题消耗多轮语义修复成本。

## 建议修正顺序（本次尚未修改共享流程）

1. 统一真实派发的输出契约：非空原文 accuracy/completeness/logic 必须逐项检查，status 为 pass/corrected；没有否定、条件或数量时，仍核对是否新增或改变关系，并据实际检查写 evidence。其余维度可在确实不适用时说明原因。
2. 明确 changes 摘录规则。若保留当前严格契约，提示词必须要求与顶层逐字相同；若以后允许每个 change 引用不同连续原文摘录，应同步修改校验器及测试，不能只改一侧。
3. 诊断采用稳定代码、字段路径、实际值、期望值和修复要求；修复任务明确补齐审校证据即可保留正确译文。保留真实审校身份，不自动补造证据，不批量改成 pass。
4. 分别报告 review_record_contract、terminology_gate、structure_gate、reported_blocking_semantic_issue，并把 regression 列为重叠标签。后续用独立的只读检查采集可安全执行的多类诊断，标明哪些检查被阻断；不要将“程序通过率”命名为“翻译正确率”。
5. 协议修正后，仅处理失败或受影响项；不重跑14,691条、不丢失已通过结论、不覆盖在途任务。对格式恢复与语义修复的计数作明确区分；任何预算调整通过公开接口和历史记录完成。
